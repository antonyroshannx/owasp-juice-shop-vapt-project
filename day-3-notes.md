# Day 3 Report: Web Application XSS Testing

## 1. Project Overview

**Project:** Vulnerability Assessment and Penetration Testing (VAPT) Lab  
**Target Application:** OWASP Juice Shop  
**Testing Environment:** Kali Linux  
**Tools Used:** Burp Suite, Firefox  
**Testing Type:** Web Application Security Testing  
**Focus Area:** Cross-Site Scripting (XSS) and HTTP Security Headers

## 2. Objective

The objective of this exercise was to understand how web applications handle user-supplied input, inspect HTTP requests and responses, identify potential Cross-Site Scripting (XSS) issues, and document security-related observations.

## 3. Testing Activities

### 3.1 HTTP Request Interception

- Opened the local OWASP Juice Shop application.
- Used Burp Suite Proxy to capture HTTP requests generated by the application.
- Inspected captured requests and responses using HTTP history.
- Identified the relevant request associated with the search input.

### 3.2 HTTP Security Header Inspection

Observed the following response header:

`X-XSS-Protection: 0`

**Observation:** The legacy browser-based XSS filter is disabled for browsers that support this header.

**Security significance:** This header is deprecated and its value alone does not establish an exploitable vulnerability. Modern XSS protection relies on controls such as context-appropriate output encoding and Content Security Policy (CSP).

### 3.3 XSS Input Testing

Submitted the following test input in the local lab:

`<iframe src="javascript:alert(\`xss\`)">`

Used Burp Suite to capture the corresponding request and inspect the HTTP response.

**Observations:**
- The test request was captured in Burp Suite.
- The submitted payload was subsequently located in the HTTP response.
- A browser alert displaying `xss` was reported during testing.

**Assessment:** These observations support further investigation of a potential XSS vulnerability. The exact execution context and relationship between the payload, response, and browser alert must be verified before assigning a confirmed vulnerability classification.

## 5. Findings and Assessment

| Finding | Observation | Assessment |
|---|---|---|
| Legacy XSS protection header | `X-XSS-Protection: 0` | Informational by itself |
| Reflected test payload | Payload found in HTTP response | Requires execution-context verification |
| Browser JavaScript alert | Alert displaying `xss` reported | Supports XSS investigation; causal link must be verified |

**Severity:** Not assigned. Severity requires confirmation of exploitability, the affected context, and potential impact.

## 6. Recommendations

- Apply context-appropriate output encoding to user-controlled data.
- Avoid unsafe DOM operations and unsafe HTML insertion.
- Configure a suitable Content Security Policy as a defence-in-depth measure.
- Validate findings using the corresponding request, response, and browser behaviour.
- Do not rely on the deprecated `X-XSS-Protection` header as the primary XSS defence.

## 7. Conclusion

This exercise provided practical experience in HTTP request interception, response analysis, security-header inspection, and preliminary XSS testing using Burp Suite.

The observations have been documented for further validation. The exercise demonstrates an understanding of the web application testing workflow and the importance of collecting evidence before classifying a security issue.
